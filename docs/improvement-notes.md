# 개선 노트

배포 후 직접 눌러 보며 찾은 문제와, 무엇을 왜 바꿨는지 기록합니다.

## 1. 상품 데이터를 한 곳으로 합침

**문제**
- 목록용 데이터(`lib/deals.ts`, 12개)와 상세용 데이터(`app/api/deals/[id]/route.ts`, 2개)가 따로 있었다.
- 3~12번 상품 상세에 들어가면 API가 404를 돌려줬고, 화면은 그 응답을 상품 데이터로 착각해 `images.map`에서 오류가 났다.
- 같은 1번 상품인데 목록과 상세의 마감 시간이 달랐다. (목록 07:31 남음, 상세 01:29 남음)

**원인**
- 같은 상품을 두 파일에 손으로 따로 적었다.
- SWR fetcher가 응답 상태(`res.ok`)를 확인하지 않았다.

**해결**
- 상세 전용 정보(이미지, 옵션, 반품 정책 등)를 id 기준으로 `lib/deals.ts`에 두고, `getDealById()`에서 기본 정보와 합쳐 반환한다. 같은 값을 두 번 적지 않는다.
- 상세 API는 `getDealById()`만 호출하고, 없으면 404를 반환한다.
- fetcher가 실패 응답이면 에러를 던지고, 화면은 404일 때 "상품을 찾을 수 없어요" 안내를 보여준다.

**이렇게 한 이유**
- 실제 서비스에서는 상품 테이블이 하나이고, 목록과 상세는 같은 테이블에서 필요한 칸만 다르게 꺼낸다.
- 데이터 접근을 `lib/deals.ts`로 모아 두면, Supabase로 바꿀 때 이 파일 안쪽만 바꾸면 되고 화면·API 코드는 그대로 둘 수 있다.

## 2. 카테고리 탭이 실제로 목록을 거르게 함

**문제**
- 탭을 눌러도 URL의 `?category=`만 바뀌고 목록은 그대로였다.
- 탭 id(`food`)와 상품 데이터 값(`식품`)이 서로 달라 연결할 기준도 없었다.

**해결**
- `lib/categories.ts`에 탭 id ↔ 상품 category 값 매핑을 한 곳에 정의했다.
- `getAllDeals`, `getDealsByTab`, `/api/deals`가 category를 받아 거른다.
- `/best`, `/today`는 서버 컴포넌트에서 `searchParams`를 읽어 반영한다.
- 오늘의 딜에서 탭·페이지를 옮겨도 카테고리가 유지되게 링크를 만든다.
- 목록이 아닌 페이지(상세 등)에서 탭을 누르면 `/best`로 이동하고, 카테고리를 바꾸면 1페이지로 돌아간다.

**이렇게 한 이유**
- 필터 상태를 URL에 두면 새로고침·뒤로가기·링크 공유에도 같은 화면이 나온다.
- 서버 컴포넌트에서 URL을 읽어 필터링하므로, 클라이언트 상태 관리 없이 처음 그려질 때부터 거른 결과가 나온다.

## 3. 반응형 레이아웃

**문제**
- 좌우 여백 120px, 4열 그리드, 상세 50:50 분할이 고정값이라 390px 화면에서 카드가 실처럼 얇아지고 메뉴 글자가 세로로 쪼개졌다.

**해결**
- 여백은 16px(모바일) → 32px(md) → 120px(lg)로 늘린다.
- 카드 그리드는 2열 → 3열(md) → 4열(lg)로 바뀐다. 스켈레톤도 같은 규칙을 쓴다.
- 헤더는 모바일에서 검색창을 아래 줄 전체 너비로 내리고, 카테고리 탭은 가로 스크롤로 바꿨다.
- 상세는 모바일에서 이미지 위·정보 아래로 쌓고, 메인 이미지는 정사각 비율을 준다.

**이렇게 한 이유**
- 커머스는 모바일 비중이 가장 크다. Tailwind의 모바일 우선 방식에 맞춰 기본값을 모바일로 두고 큰 화면에서 늘린다.

## 4. 카테고리를 코드값으로 저장

**문제**
- 카테고리 하나에 이름이 세 개였다: URL `beauty`, 탭 글자 `뷰티/건강`, 상품 데이터 `뷰티`.
- 상품 데이터에 화면용 한글이 들어 있어서, URL 값을 데이터 값으로 바꾸는 번역 함수(`getCategoryValue`)가 따로 필요했다.

**해결**
- 상품 데이터의 `category`를 URL과 같은 코드(`fashion`, `tech`, `beauty`, `food`, `living`)로 바꾸고 `CategoryId` 타입으로 묶었다.
- 화면에 보일 때만 `getCategoryLabel()`로 이름을 붙인다 (카드, 상세).
- URL 값은 `isCategoryId()`로 실제 코드인지 확인한 뒤 그대로 거른다. 번역 단계가 없어졌다.

**이렇게 한 이유**
- 실무 DB는 코드를 저장하고 화면 이름은 따로 관리한다. 화면 이름을 바꿔도 상품 데이터는 그대로 두면 되고, 다국어도 라벨만 추가하면 된다.
- 타입을 `string`에서 `CategoryId`로 좁혀서, 오타가 난 카테고리는 TypeScript가 바로 잡아 준다.
- Supabase로 옮길 때 `category` 칸에 이 코드를 그대로 넣으면 된다.

## 5. 잘못된 시각 값이 화면 문구와 베스트에 새지 않게 함

**문제**
- 홈 규칙 함수를 `/jest-test`로 검사하면서 "이상한 입력" 경우를 넣어 보니, 날짜가 아닌 시각 문자열에서 세 군데가 틀렸다.
  - `formatEndLabel`이 `"NaN월 NaN일 NaN:NaN 마감"`을, `formatKstTime`이 `"NaN:NaN"`을 돌려줬다.
  - 오픈 시각만 잘못된 딜이 오늘 마감·곧 오픈에서는 빠지는데 베스트에는 남았다.

**원인**
- `new Date("abc")`는 오류를 던지지 않고 Invalid Date를 만든다. 그 값의 `getTime()`은 `NaN`이고, NaN과의 비교(`<`, `<=`, `>`)는 항상 false다.
- 그래서 `formatEndLabel`은 앞의 조건을 모두 지나쳐 마지막 "M월 D일" 분기로 빠졌다.
- `selectHomeSections`의 `live`는 `endTime > now`만 봤다. 오픈 시각이 NaN이면 오늘 마감(`openTime <= now`)과 곧 오픈(`now < openTime`) 둘 다 false라 우연히 빠졌지만, 베스트는 `live` 전체에서 고르므로 남았다.

**해결**
- `lib/dealTime.ts`: 시각이 Invalid Date면 먼저 돌려준다 (`"마감 시간 미정"`, `"--:--"`).
- `lib/home.ts`: `live`를 만들 때 오픈 시각이 올바른 딜만 남긴다. 마감 시각이 NaN인 딜은 원래 `endTime > now`에서 빠진다.

**이렇게 한 이유**
- 지금은 목 데이터라 이런 값이 없다. 처음에는 관리자 입력 검사 단계까지 미루려 했지만, 데이터가 어디서 오든 화면 함수는 스스로 방어해야 한다고 판단했다. 곧 Supabase·관리자 입력으로 데이터가 바뀐다.
- NaN은 조용히 퍼진다. 비교가 전부 false가 되므로 "어느 조건에도 안 걸리는" 값이 되고, 영역마다 결과가 달라진다. 경계에서 한 번 거르면 아래 규칙은 올바른 값만 다룬다.

## 6. 카드의 카운트다운을 마감 시각 문구로 바꿈

**문제**
- 목록 카드(`DealCard`)가 사진 위에 `03:12:45`처럼 초 단위로 줄어드는 카운트다운을 띄웠다. 재촉하는 느낌이 강하고, 몇 시에 끝나는지는 오히려 계산해야 알 수 있었다.
- 사진에 흑백·어둡게 필터가 걸려 상품이 잘 안 보였고, 사진 위에 아무 역할 없는 덮개 `div`가 있었다.
- 사진 6장이 상품명과 맞지 않았다 (이어폰에 선글라스, 에어팟에 헤드폰, VR 헤드셋에 손목시계, 선글라스에 운동화, 식용유에 향수, 무선청소기에 로봇청소기).

**원인**
- 카운트다운(`DealTimer`)은 1초마다 `setInterval`로 다시 그리므로 클라이언트 컴포넌트여야 한다. 그래서 카드 하나하나가 브라우저 JS를 끌고 왔다.
- 필터와 덮개는 처음 만들 때 글자를 사진 위에 얹으려고 넣은 것이 카운트다운만 남은 뒤에도 그대로 있었다.

**해결**
- `DealCard`가 `now`를 받아 `formatEndLabel(endTime, now)` 결과를 가격 아래에 보여준다. 평소에는 회색 "오늘 20:00 마감", 1시간 미만이면 빨간 "곧 마감 · 20:00", 지났으면 "마감".
- `now`는 페이지(`/today`, `/best`의 `DealCardGrid`)가 한 번 만들어 내려준다.
- 필터·덮개를 지우고, 맞지 않는 사진은 직접 받아 보고 상품에 맞는 사진으로 바꿨다 (상세 사진 중 다른 상품인 것도 뺐다).
- `DealTimer`는 상세 페이지가 아직 쓰므로 남겼다 (상세 정리 때 함께 본다).

**이렇게 한 이유**
- 시각만 보여주면 초마다 바뀔 것이 없으므로, 카드가 서버 컴포넌트로 남고 카운트다운용 JS가 목록에서 빠진다.
- `now`를 카드 안에서 `new Date()`로 만들지 않고 받는 이유: 한 화면의 모든 카드와 목록 거르기가 같은 순간을 기준으로 삼고, 테스트에서는 `now`만 바꿔 "30분 전", "지남"을 바로 확인할 수 있다.
- 서버에서 그린 시각 문구라 페이지를 오래 띄워 두면 "곧 마감"으로 저절로 바뀌지는 않는다. 다시 들어오거나 새로고침하면 맞춰지므로, 이 정도는 카운트다운의 비용보다 낫다고 판단했다.

**같이 고친 것: 할인율 0 (`/jest-test`로 찾음)**
- 카드가 조건 없이 `{discountRate}%`를 그려, 할인 없는 상품에 빨간 "0%"와 판매가와 같은 취소선 가격이 나왔다. 상세 화면(`DealInfos`)은 11-17에 이미 `discountRate > 0`으로 고쳤는데 카드에는 같은 규칙이 없었다.
- 카드도 `discountRate > 0`일 때만 할인율과 취소선 가격을 그린다. 취소선 줄은 빈 칸으로 남겨 목록에서 카드 높이가 들쭉날쭉하지 않게 했다.
- 같은 규칙이 화면마다 따로 있으면 한쪽만 고쳐진다. 지금은 두 곳뿐이라 그대로 두고, 가격 표시가 세 번째 화면(홈 곧 오픈·베스트)에 생기면 가격 표시 컴포넌트로 합칠지 module-3에서 본다.

## 7. 임시 홈 화면을 배너·오늘 마감·곧 오픈·베스트로 바꿈

**문제**
- 첫 화면(`/`)이 `home page` 글자와 `Click me` 버튼뿐이라, 배포 링크로 들어온 사람이 무슨 사이트인지 알 수 없었다.

**원인**
- 목록(`/today`, `/best`)과 상세를 먼저 만들고 홈은 자리만 잡아 두었다. 어느 딜을 어느 영역에 보여줄지 정한 규칙도 없었다.

**해결**
- 홈을 서버 컴포넌트로 다시 만들었다. 맨 위 기획전 배너(최대 5장, 자동 넘김), 오늘 마감(마감 빠른 순 6개), 곧 오픈(오픈 시각 순 15개를 5개씩), 베스트(리뷰 순 15개를 5개씩, 순위는 장을 넘어 이어짐).
- 어느 딜이 어느 영역에 들어가는지는 `lib/home.ts`의 순수 함수 `selectHomeSections(deals, banners, now)`가 정하고, 화면 컴포넌트는 받은 결과를 그리기만 한다.
- 배너는 딜이 아니라 운영자가 정하는 기획전 데이터(`Banner`, `lib/banners.ts`)로 따로 두었다. 누르면 `/best?category=`로 간다.
- 브라우저로 가는 JS는 캐러셀 하나(`PagedCarousel`)뿐이다. 배너·곧 오픈·베스트가 같이 쓰고, 자동 넘김은 배너만 켠다.
- 첫 계획서와 다르게 바뀐 점: 처음에는 맨 위를 "마감 빠른 딜 3개"로 하려 했는데, 그러면 오늘 마감 목록과 같은 딜이 두 번 나오고 거의 끝난 딜이 대표 자리에 오른다. 11번가 홈을 보고 배너를 운영자가 고르는 기획전으로 바꿨다.

**이렇게 한 이유**
- **요청마다 그리기 (`force-dynamic`)**: 홈은 `searchParams`를 읽지 않아서 그대로 두면 빌드할 때 한 번 그려져 "지금 시각"이 빌드 시각에 멈춘다. `revalidate`(ISR)는 오래된 화면을 먼저 보여주고 뒤에서 새로 그리는 방식이라, 방문이 드문 포트폴리오에서는 첫 방문자(면접관)가 몇 시간 전 화면을 본다. 목 데이터 거르기는 몇 ms라 요청마다 그려도 비용이 거의 없다. Supabase 단계에서는 페이지 대신 DB 조회 결과를 캐시하고, 시간 판단은 계속 요청마다 한다.
- **children으로 넘기는 서버/클라이언트 경계**: 캐러셀은 넘김 상태가 있어 클라이언트여야 하지만, 그 안의 카드·장은 서버에서 그려 `children`으로 넘긴다. 클라이언트 파일이 카드를 직접 import하면 카드까지 클라이언트 JS가 된다. children으로 받으면 캐러셀은 이미 그려진 결과를 옆으로 옮기기만 한다 (`nextjs-rendering-guide.md` 3-1).
- **시각은 한 번만**: 페이지가 `now`를 만들어 거르기 함수와 카드에 내려준다. 한 화면의 모든 판단이 같은 순간을 기준으로 하고, 테스트에서는 `now`만 바꿔 "마감과 같은 순간", "자정 직전"을 바로 확인할 수 있다. 분석 단계에서 `/today`의 `getDealsByTab`이 자기 `now`를 따로 만들던 것도 같이 맞췄다.
- **자동 넘김 훅을 직접 만듦 (`useAutoplay`)**: embla의 autoplay 플러그인을 쓰면 의존성이 하나 늘고 동작이 라이브러리 안에 숨는다. `setInterval` 하나를 관리하는 짧은 훅이라 직접 만들고 가짜 시간으로 따로 테스트했다. 손으로 넘기면 현재 장 번호(`resetKey`)가 바뀌어 타이머가 처음부터 다시 센다. 그래서 넘기자마자 또 넘어가지 않는다. 콜백은 `useEffectEvent`로 감싸, 렌더마다 새 함수가 와도 타이머를 다시 만들지 않는다.
- **동작 줄이기를 `useSyncExternalStore`로 읽음**: 렌더 중에 `window.matchMedia`를 바로 읽으면 서버 HTML(값을 모름)과 브라우저 첫 렌더가 달라져 hydration 불일치가 난다. `useEffect`에서 읽어 `setState`해도 맞지만, 값을 옮겨 담는 state와 effect가 하나씩 늘고 설정이 바뀌는 것은 따로 구독해야 한다. `useSyncExternalStore`는 hydration 동안 서버 값(`false`)을 쓰고 그 뒤 실제 값으로 다시 그리며, 설정이 바뀌면 따라간다. 사용자가 재생·일시정지를 누르면 그 선택이 설정보다 우선한다.
- **읽는 중에는 멈춤**: 마우스가 올라가 있거나 키보드 포커스가 캐러셀 안에 있으면 넘기지 않고, 재생 중에는 장 번호를 스크린리더가 읽지 않게(`aria-live="off"`) 했다. 5초마다 읽어 대면 다른 내용을 들을 수 없다 (WAI 캐러셀 패턴).
